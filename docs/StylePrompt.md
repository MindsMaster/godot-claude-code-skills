# 编码协作规范

本文件给 AI 编码助手或新成员使用，适用于任意语言和技术栈。放进项目的 `CLAUDE.md`、`AGENTS.md`、`.cursorrules` 或系统提示词即可。尖括号 `<...>` 处按项目替换。

# 注释

## 默认不写

常量、局部变量、字段、函数、类型，默认零注释。名字已经说出来的事不再复述。

不写函数头和文件头的概述块。不写"这个函数做什么"、不写设计意图、不写性能收益、不写实现步骤、不写调试史。"之前因为 xx 导致 yy，现在改成 zz"属于 commit message，不属于源码。

目标密度：普通逻辑文件每 70 行约 1 条。

## 四类例外

只有这四类值得写：

1. 跨文件或跨语言的同步约束。改 A 必须同时改 B，否则静默出错。
   `/** 与 theme.css 的过渡时长一致 */`
2. 外部契约事实。值来自序列化格式、操作系统 API、数据库列、第三方接口，仓库里查不到。
   `/// 字段缺省时服务端回退为 id`
3. 名字与实际不符。
   `# 实为事件驱动 非轮询`
4. 真陷阱。照直觉写就会出 bug。
   `// 代理对象不可结构化克隆 须先转普通对象`

历史遗留要分清：描述真实存在的外部旧物（老安装包、老注册表键、老数据目录、老配置文件、老进程名）属于例外 2，保留。解释当初照着某个已经不存在的旧实现抄了什么，属于心路历程，删。

数据契约文件（DTO、schema、配置结构）按字段算密度而不是按行，保留约四分之一字段的注释是合理的。

## 形式

保留的注释若描述的是紧跟其后的项，用该语言的 doc 形式：Rust `///` 与模块级 `//!`，TypeScript/JavaScript `/** */`，Python docstring，Go 紧贴声明的 `//`，C# `///`，Java/Kotlin `/** */`。普通行注释只用于函数体内部和语句之间。

删掉叙述性文档块不等于把 doc 注释降级成行注释。要么整条删掉，要么保持 doc 形式。

保留的注释是路标不是解释，给代码块起个名，不论证为什么。长度不超过 15 个汉字或约 8 个英文单词。

不用句号。逗号分号冒号换成空格。不用括号补充。不写破折号和引导词。理由压成名词短语，不展开机制、不写数字、不写因果链。

不用分节符。不用加粗、箭头、编号列表。

## 落点

只在代码读起来像是多余或随意的地方留注释：一串魔法字符串或选择器，一个看着重复可以删掉的监听或分支，一层莫名的间接（异步调度、延时、额外的对象拷贝）。

## 各类文件

系统语言（Rust、C、C++、Go）：doc 注释同样按上面处理，内部库不对外发布，不需要叙述式文档。`unsafe` 的 Safety 说明保留，这是硬约定。系统 API 的参数语义、必须成对调用的 API 属于例外 2 和 4。

样式文件（CSS、SCSS、Less）：几百行的样式文件可以留分区标题，但不用 `---` 之类的分节符，也不带序号。写 `/* 编辑抽屉 */` 不写 `/* --- 面板5 闹钟 --- */`。标题与文件名重复的整条删。单条属性的解释删掉。

安装器、构建脚本、CI 配置：注释多属例外 2，从宽保留。

测试：断言不带长说明，测试名本身就是说明。打印实际值的诊断参数保留。

## 不是注释

不准当成注释删改：lint 抑制指令（`eslint-disable`、`# noqa`、`#[allow]`、`//nolint`）、类型检查指令（`@ts-expect-error`、`# type: ignore`）、格式化器指令（`prettier-ignore`、`# fmt: off`）、语言属性和注解、许可证头、构建指令（`//go:build`、shebang、编码声明）。

被注释掉的死代码直接整块删除。

## 样板

已经是目标状态的文件：`<列出项目里 2 到 5 个风格达标的文件路径>`。新写代码照着它们的手感。

# 代码

- 不为一次性操作抽 helper，不为假想的未来需求做抽象。
- 不加防御性校验内部代码不可能出现的情况。只在系统边界校验：用户输入、外部进程、网络、文件。
- 不留探针、诊断日志、被推翻假设下加的"修复"。问题定位完成后一并清掉。
- 修复问题前先确认根因，能用数据证明再动手。不连续叠补丁，一个补丁没解决就回头重新定位。
- 新代码读起来要像周围的代码：命名、惯用法、注释密度与所在文件一致。

# 排查

- 先用离问题最近、噪音最低的工具：应用自带日志、浏览器 DevTools 与 HAR、语言自带 profiler、单测复现。全系统 trace 和抓包放到最后。
- 需要对方操作工具时，步骤写到点哪个按钮、导出什么文件，不假设对方熟悉该工具。

# 提交信息

格式：`type(scope): 一句话`，不带正文。

- type：feat / fix / perf / refactor / chore。
- scope：受影响的模块或领域，如 auth、api、build、ui；跨域可省略。
- 一句话说结果，不说机制。
- 措辞简短书面，用"修复…问题""优化…开销""新增…""改为…"这类短句。不写口语，不写"卡好几秒"这类描述。
- 需要补一个分句时用空格隔开，不用逗号句号展开。
- 一个 commit 一件事。多个不相关改动分开提。

好的：

```
fix(ui): 修复面板聚焦时点击设置阻塞问题
perf(player): 封面改走本地协议直出 不再经接口传 base64
feat(weather): 天气可按选中城市拉取 未选时沿用自动定位
refactor(api): 鉴权开关收归后端单一入口
```

不好的：

```
fix(ui): 修复面板打开时点设置要卡好几秒才弹出的问题，原因是 xxx
fix(update): 在 install 前增加 confirm 弹窗并移除自动 restart 调用
```

# 验证

交付前跑全套检查：`<类型检查> && <lint> && <测试> && <构建>`。格式化用项目配置的格式化器，不手调格式。

本地环境编不了的部分，只做可静态证明的改动，并在交付时明确说明哪些未编译、未运行。测试失败照实报告并附输出，不说"应该没问题"。

# 沟通

- 面向人的回复用 `<中文>`。代码、标识符、日志原文保持原样。
- 先给结论，再给必要细节。不复述需求，不在结尾重复总结。
